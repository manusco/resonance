# GitHub repository and Actions

Research checked against official GitHub documentation on 2026-10-13. Repository plans, visibility, organization policy, and runner setup affect feature availability. Inspect settings before claiming a control is active.

## Repository governance

Protect the default and release branches with pull requests and the status checks that actually guard changes. Use stable, unique check names, and confirm each check reports on a candidate commit before requiring it. Choose branch protection for a repository rule or rulesets for policy across branches or repositories. Set review count, CODEOWNERS, stale-approval dismissal, and bypass actors to fit reviewer capacity and change risk. Keep bypass narrow and auditable. See [protected branches](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches), [rulesets](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/available-rules-for-rulesets), and [CODEOWNERS](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/customizing-your-repository/about-code-owners).

## Workflow security

Declare the minimum `GITHUB_TOKEN` permissions needed. Once a permissions map is present, omitted permissions become `none`; grant writes only to the job that needs them. For fork contributions, validate with `pull_request` and a read-only token. Treat pull request code and artifacts as untrusted. Never check out or execute that code in privileged `pull_request_target` or `workflow_run` jobs. Do not expose secrets to untrusted pull request code. Pass event data through environment variables, then validate it before use. Prefer GitHub-hosted runners for untrusted contributions; isolate and replace self-hosted runners if they must process them. See [token permissions](https://docs.github.com/en/actions/tutorials/authenticate-with-github_token?force_isolation=true), [secure use](https://docs.github.com/en/actions/reference/security/secure-use), and [safe use of `pull_request_target`](https://docs.github.com/en/actions/reference/security/securely-using-pull_request_target).

Pin third-party actions to verified full commit SHAs and review updates through Dependabot or an equivalent process. Use OIDC when a workload needs cloud access and the provider supports federation. Give `id-token: write` only to that job, and constrain the cloud trust policy to the expected repository, branch, and protected environment. The permission allows a workflow to request an identity token; the cloud trust policy controls access. See [pinning actions](https://docs.github.com/en/actions/how-tos/write-workflows/choose-what-workflows-do/find-and-customize-actions) and [OIDC](https://docs.github.com/en/actions/concepts/security/openid-connect).

## Required checks and merge queues

Avoid path or branch filters that skip a required workflow and leave its check pending. Keep a stable required check reporting for each candidate. When a merge queue is enabled, every workflow that supplies a required check must also handle `merge_group`. Use a queue when concurrent pull requests often invalidate one another; otherwise requiring branches to be up to date may be simpler. See [merge queues](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/configuring-pull-request-merges/managing-a-merge-queue) and [required-check troubleshooting](https://docs.github.com/en/pull-requests/how-tos/merge-and-close-pull-requests/troubleshooting-required-status-checks).

## Reliability and cost

Set job timeouts from observed duration with a safe buffer. A low limit creates flakes; an excessive limit permits runaway work. Cancel superseded branch CI only when it is safe, and include the workflow name in concurrency groups to avoid unrelated workflows cancelling one another. Serialize deployments by environment; do not cancel an active release unless its platform supports safe cancellation. Use matrix legs when they add compatibility evidence, and choose fail-fast based on whether the remaining diagnostics are useful. Cache package downloads only when keys and trust boundaries are safe. A cache is an optimization, not a test result or trusted build artifact. Check current billing for the plan, runner type, and operating system before estimating cost. See [workflow syntax](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax), [concurrency](https://docs.github.com/en/actions/how-tos/write-workflows/choose-when-workflows-run/control-workflow-concurrency), [dependency caching](https://docs.github.com/en/actions/concepts/workflows-and-actions/dependency-caching), and [Actions billing](https://docs.github.com/en/billing/concepts/product-billing/github-actions).

## Releases and provenance

Run release jobs only from reviewed, protected source. Keep build and test jobs unprivileged; grant publish permissions to the final job. Use environment reviewers or branch restrictions when supported and part of the release process. Checksums help detect file changes; attestations bind provenance claims to an artifact. Generation alone does not prove an artifact is safe. Give consumers verification instructions, such as `gh attestation verify PATH/TO/ARTIFACT -R OWNER/REPOSITORY`, with signer constraints when policy requires them. GitHub's immutable releases setting is separate and disabled by default; an ordinary published release is not immutable. See [deployment environments](https://docs.github.com/en/actions/how-tos/deploy/configure-and-manage-deployments/manage-environments), [artifact attestations](https://docs.github.com/en/actions/concepts/security/artifact-attestations), and [immutable releases](https://docs.github.com/en/code-security/concepts/supply-chain-security/immutable-releases).
