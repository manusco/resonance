# Complexity and simplicity in the Resonance workflow

**Date:** 2026-10-14
**Question:** What evidence supports stronger complexity-reduction guidance across Resonance workflows, architecture, and interface design, and how can that guidance avoid scope cuts, unsafe simplification, and false precision?
**Status:** Research recommendation, not a source change.

## Recommendation

Add one shared, outcome-preserving review method to the workflow and point planning, architecture, build, and design skills to it. Do not install a universal “complexity score,” promise that complexity is conserved, or invent a named bound that implies a formal result.

The review method should make the operator map the work and its burdens, preserve the agreed outcome and invariants, then consider deletion, reuse, absorption, redesign, optimization, and selective automation. It should ask for evidence before retaining each step or layer, while treating a valid requirement as in scope until the user changes it. Simplification can change who bears the work, introduce migration and operational risk, or change domain behavior. “Do nothing” is a valid recommendation when the expected reduction does not outweigh those costs.

## A practical review method

1. **State the fixed outcome first.** Copy the user-approved goal, constraints, and non-goals. Tag each constraint as settled, directly requested, or inferred. An inferred constraint can be challenged; an in-scope user requirement cannot be silently deleted. Recommend a scope change and get the user’s decision before changing the contract.
2. **Map the current burden.** Trace the user-visible path, implementation layers, handoffs, permissions, persistent state, audit trail, and failure/recovery steps. For each one, record who does the work, why it exists, frequency, consequence of failure, and evidence. Mark unknowns instead of inventing reasons.
3. **Name the invariants.** List behavior that must survive, such as authorization checks, data ownership, state transitions, audit evidence, recovery, accessibility, and external contracts. These define the boundary for simplification. A feature removal or data migration that changes an invariant is a scope or architecture decision, not routine cleanup.
4. **Compare the smallest viable options.** For each burden, consider: delete it; reuse an existing capability; absorb it into an existing layer; redesign the domain or flow so the work is unnecessary; simplify the remainder; optimize it; or automate it selectively. Include “keep it” when it protects a requirement or when transition cost exceeds expected benefit. Do not require every option or step to be exercised.
5. **Track burden movement and transition cost.** Describe what each option adds to or removes from users, operators, developers, platforms, support, and auditors. Include migration, training, rollback, and maintenance costs. A lower user burden that creates a fragile operator burden is not automatically a net reduction.
6. **Set a falsifiable prediction before implementation.** Choose an observable outcome that matches the task: fewer actions or handoffs, less time, fewer errors, a clearer mental model, faster recovery, fewer maintained components, or lower operational toil. Record the baseline, population or representative task, and what result would disprove the claim. If an outcome arrives later, set a due date and wait for it before declaring the reduction proven.
7. **Verify invariants and the predicted outcome.** Run the task paths and applicable checks. Include denial and error cases, state persistence, auditability, rollback or recovery, keyboard and assistive-technology access, and realistic responsive widths where relevant. If a predicted improvement does not appear, restore, revise, or report the result rather than treating deletion itself as success.

### Example: a multi-step approval workflow

Before: a requester enters the same project details in a form, a reviewer copies them to a tracker, an administrator checks permission in a separate step, and a support operator repairs incomplete records manually. The purpose and failure behavior of each step are currently undocumented.

Review: map the data and authority for each handoff. Preserve the approved requester/reviewer roles, permission enforcement at the trusted boundary, status history, and a recovery path for failed submissions. Check whether an existing project record can supply repeated fields, whether the tracker is a duplicate system of record, and whether validation can happen at entry. Do not remove the reviewer’s approval or administrator control merely because they add clicks; first establish whether each is a user requirement, a control, or an accidental process.

Prediction: on a representative set of approvals, reduce duplicate entry and median completion time while keeping authorization-denial behavior, status history, and recovery success unchanged. If those controls cannot be demonstrated after a proposed redesign, the proposal fails even if it has fewer steps.

## Where this fits in Resonance

The existing workflow already protects scope provenance and user authority. `/goal` separates outcome, directives, inferred tactics, constraints, and non-goals; `/plan` maintains approved scope and adds architecture, security, and verification constraints; `/build` executes only an approved plan. The new guidance should reinforce these contracts, not add an approval ceremony to routine work.

The architecture skill can own the burden and invariant map when boundaries, contracts, ownership, or migrations change. The design skill can apply the same method to user-visible steps, information retrieval, cognitive effort, and recovery, then keep its current real-path and accessibility checks. The plan skill can ask for baseline, intended reduction, and falsifier when “simpler” is an explicit outcome. The build skill needs no new gate; it should implement only the approved option and verify the invariants already in the plan.

Suggested shared vocabulary: **burden map**, **outcome invariant**, **burden transfer**, **transition cost**, **baseline**, **falsifier**. Avoid a generic “complexity budget” unless a project defines a concrete unit and decision use. Component count, click count, lines of code, cognitive load, coupling, and operational toil are different measurements; combining them into one score would hide tradeoffs.

## Limits and evidence gaps

- “Essential” and “accidental” are scope-relative judgments. A redesign can reduce what was previously unavoidable, so classify current work rather than declaring whole domains irreducible.
- Complexity, effort, usability, reliability, and maintenance burden need separate observable measures. The sources do not provide a common scale for combining them.
- The source base includes influential essays, books, and practitioner heuristics. They motivate questions and caution; they do not validate a deterministic sequence for every project.
- The cognitive-load model concerns learning. Applying its categories to workflow design is an analogy unless the task is explicitly instructional and measured accordingly.
- A broad scan of every Resonance skill and empirical usability/security studies was outside this research pass. The recommendations target the orchestration, planning, architecture, build, and design paths inspected here.
