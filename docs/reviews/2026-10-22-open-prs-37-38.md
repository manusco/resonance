## PR #37

The QA skill already tells reviewers to select an E2E strategy for user journeys, use a real browser for live verification, and report observed evidence. It does not explain how to scope an exploratory first-run journey or how to talk about recurrence from a small sample. The new section at `.agents/skills/ops/qa/SKILL.md:56-60` supplies that useful method: choose audience-relevant perspectives, follow the critical path through first meaningful success, record reproducible evidence, merge duplicates, rank by observed recurrence and impact, disclose the sample size, then rerun reviewed fixes. It explicitly avoids a fixed persona quota, mandatory parallel work, exhaustive screenshots, and one-pass fixes.

The behavior is appropriately scoped to exploratory usability work. The sample-size caveat prevents a small round from being presented as a population estimate. Existing guidance on 8-path coverage, the test-value gate, and live browser checks remains in force. The template mirrors the canonical skill. ### Finding 1: Browser-only execution for every first-run journey

**Category:** Verification Quality. **Severity:** P2. **Confidence:** High.

**What this is:** The added instruction says to use a real browser for exploratory first-run QA without limiting that direction to web apps (`.agents/skills/ops/qa/SKILL.md:56-60`). The query for the new eval says only “self-serve app,” so it does not constrain the target to web.

**Problem:** For a native iOS or Android journey, a browser cannot render or exercise the shipped app. A reviewer following this blanket instruction can end with no valid first-run evidence, or use a web wrapper and miss native behavior. Existing project guidance explicitly calls for native rendering and interaction evidence and says browser screenshots are not required for native UI (`.agents/skills/engineering/mobile/evals/07_design_contract_native_variants.json:3-10`). The QA live-execution reference's browser loop is for a web surface; the broader QA skill covers user-facing flows generally (`.agents/skills/ops/qa/SKILL.md:45-48,102`; `.agents/skills/ops/qa/references/live_execution.md:24-32`).

**Fix:** Scope the new eval query to a self-serve web app. In the instruction, require the real target app and platform-appropriate interaction evidence: browser for web, device or simulator for native mobile, and the app's native surface for desktop. Add a native first-run QA eval (or extend a QA-owned mobile case) that rejects a browser-only requirement and expects the target platform's evidence.

**If we skip it:** Native first-run reviews can be blocked or can miss problems that exist only in the shipped app.

**Disposition:** request this narrow scope fix, then integrate. The exploratory method itself is valuable and should remain.

## PR #38

The security review protocol already says to isolate untrusted source and avoid live secrets, and it already prevents claims based on deployment facts that are not visible in source. It does not define the execution boundary or retained-artifact rules. The new section at `.agents/skills/ops/security/references/agentic_vulnerability_review.md:33-40` closes that gap by requiring host-enforced network, filesystem, environment, and resource controls; refusing target execution when a required control is missing; keeping execution-dependent claims in `needs validation`; and treating target-written outputs as untrusted until bounded, race-safe host checks pass.

This fits the security skill's existing source-visibility and candidate-validation gates. The fail-closed condition is intentionally strict: when an environment cannot enforce those controls, a security review remains source-only and names the missing control plus an owner check. The adjacent workflow still supports source review and does not require target execution to complete it. The generated reference mirrors the canonical file. The new eval exercises absent network/write isolation, source-only continuation, validation status, and unsafe wholesale artifact copying.

The PR reports targeted security eval-structure and manifest checks, not a live security behavior score. The harness distinction is documented in `.forge/run_evals.py:8-16`; the report makes no behavioral-lift claim. GitHub's five reported checks all succeeded.

**Disposition:** clean; integrate as-is. No confirmed security or runtime defect in the guidance change.
