# State of Resonance: Detailed Analysis (2026-07-03)

> A file-level audit of the whole framework: what is state-of-the-art, what is weak, where it drifts, where it is bloated, how it compares to the latest GStack (v1.58.5), and whether to add loop engineering (a `/goal` command). Companion to `RECOMMENDATION_V3.md` and `GSTACK_TEARDOWN.md`.

## 0. The one-paragraph verdict

Resonance is now a genuinely strong, cross-tool skill framework that has quietly executed almost its entire v3 roadmap. The two things v3 said were missing and defining, a deterministic validator and a compiler, both exist and work; the skill/workflow confusion is resolved into three archetypes; the token budget is disciplined; slash commands are cross-tool and clone-and-go; and the business-domain breadth (sales, marketing, strategy, design, ops) is wider than any comparable framework including GStack. The gaps are no longer architectural, they are about execution surfaces and hygiene: the evals are authored but never run (there is no eval runner), the agent has no eyes (no browser or test execution loop), memory is read-whole-file with no recall-by-meaning, and the reference libraries have grown faster than their upkeep, leaving 45 orphaned files, a fully duplicated skill-author, a diverged `style_matrix`, and one real philosophical contradiction I introduced when I rebuilt the designer. None of these are hard to fix. The framework is past the "is it real" question and into the "make it elite and keep it clean" phase.

## 2. Where Resonance is state-of-the-art

- **The compiler is the differentiator.** One source, emitted per tool and per model, with shared sections injected from resolvers and a static validator gating every output. This is the same architecture as GStack, in pure-stdlib Python instead of a Bun/TS build graph, which makes it simpler to reason about and genuinely cross-platform. Very few skill libraries have this; most are folder dumps.
- **Token discipline.** The operating standard (voice, decisions, completion, ratchet) is stated once in the always-loaded `AGENTS.md` and referenced by a one-line pointer per skill, instead of being re-injected into all 47. This is leaner than GStack, which tolerates 25 to 35K-token skills on prompt-caching grounds.
- **Operational rigor the bare standard lacks.** Every procedure skill carries Input, Output, Definition of Done, and Recovery. The debugger's "no fix without a reproduction that fails 100% of the time," the reviewer's P0-P3 harm-ranked taxonomy, the qa 8-Path Matrix, and the "escalate after 3 tries" ceiling are all real, and match or beat GStack on the rigor that matters.
- **Business-domain breadth.** GStack is a coding factory. Resonance also covers sales, marketing, GTM, venture modeling, and research. For a founder who builds and sells, this is a wider, more valuable surface.
- **The `.resonance/` memory model.** Externalized cognition (soul, state, memory, systems, learnings) predates the "agent memory" product category and is still ahead of most frameworks conceptually.
- **The rebuilt designer.** After this session, `design/designer` is a first-principles design authority (optical craft, perceptual color, motion physics, cross-canvas, copy-as-interface) that is genuinely 1% and beats GStack's design skills on craft depth.
- **Clone-and-go distribution.** The command shims are committed, so the slash commands work on clone with no build step. GStack needs Bun plus platform-specific binaries.

## 3. Where it is weak, and the real holes

### 3.1 Evals are authored but never executed (the biggest hole)
Every skill ships >=3 golden cases in `evals/*.json`, and `validate_skill.py` checks they exist. But there is **no runner**. `.forge/` has `forge.py` and `validate_skill.py` and no `run_evals.py`. So the golden cases are documentation, not a measurement. The whole point of eval-first ("prove the skill closes a gap, measure with vs without") is unrealized. This is the single highest-leverage fix, and it also unlocks loop engineering (a grounded verifier), see section 8. GStack already has the four-tier harness (static, LLM-judge, E2E, planted-bug fixtures) as a blueprint.

### 3.2 The agent has no eyes (no execution surface)
`/test` (`ops/qa`) is a test-*plan* skill: the 8-Path Matrix, property-based strategy, assertion layers. It never runs anything. There is no browser, no screenshot, no headless execution. GStack's biggest unlock, by Garry Tan's own account, was `/qa` opening real Chromium to reproduce, fix, and re-verify bugs with screenshots. Resonance plans tests; it cannot see. This is the largest capability gap versus GStack and versus the whole SWE-bench-verified generation of agents, whose gains (from under 10% to over 70% in a year) came almost entirely from iterating against *executed* tests.

### 3.3 Memory is read-whole-file, with no recall-by-meaning
`.resonance/` is flat Markdown (`00_soul` through `04_systems`, plus `guards.json` and `learnings.jsonl`). The agent reads whole files at task start. There is no semantic index ("what did we decide about auth?"), no event-sourced decision log with supersede/redact semantics, and no cross-session vector recall. As the memory grows, whole-file reading degrades. GStack's gbrain (semantic search plus `decisions.jsonl`) is the proof point. Note also a small documentation drift: the README's memory table lists only `00_soul`, `01_state`, `02_memory`, `learnings.jsonl`, but the real structure also has `03_tools`, `04_systems`, and `guards.json`.

### 3.4 No deterministic enforcement layer (hooks)
The Four Locks and 4 Zeros are enforced by prose, which is Layer 1 (probabilistic), the exact thing Resonance's own philosophy says to push to Layer 3. Where a runtime offers hooks (Claude Code does), the enforceable ones should be: block a ship without a passing test, run the banned-phrase scan on generated copy, refuse a commit touching `00_soul.md`. There is no `.claude/hooks` and no hook config. v3 flagged this; it remains open. It is an enhancement, not a foundation, but it is the difference between preaching determinism and enforcing it.

### 3.5 No multi-model second opinion
Resonance ships GPT, Gemini, and open-weights *overlays*, so the compiler can target other models, but there is no live second-opinion call. GStack's `/codex` runs an independent OpenAI review of a diff and computes finding-overlap with Claude's review. Cross-model disagreement catches bugs a single model rationalizes away. Resonance has the overlay infrastructure to make this nearly free and does not use it.

### 3.6 No post-ship verification
`/ship` stops at tag, changelog, and push. There is no deploy verification, no canary, no post-deploy health check, no performance-regression gate. GStack's `/land-and-deploy` waits on CI and deploy, then health-checks production.

## 7. GStack comparison (latest, v1.58.5)

GStack updated from v1.28 to v1.58.5 (60 commits, ~7 weeks). It is now 59 skills, 119k stars, a Bun/TS monorepo with a real browser binary, a design image CLI, a Chrome extension, and gbrain memory. Philosophically it is a near-twin of Resonance (Boil the Ocean = Boil the Lake, User Sovereignty, Iron Law, escalate-after-3). Architecturally it is the same species: a template-plus-resolver-plus-host-plus-overlay compiler.

**Where GStack is ahead:** real browser QA execution (the big one), semantic + event-sourced memory (gbrain, `decisions.jsonl`), multi-model second opinion (`/codex`), per-*version* model overlays (`opus-4-7`, `gpt-5.4`), a design-to-HTML visual pipeline with taste memory, auto-doc-drift (`/document-release`), deploy verification (`/land-and-deploy`, `/canary`), and cross-vendor multi-agent (`/pair-agent`, worktree spawning).

**Where Resonance is ahead:** business-domain breadth, token discipline (state the standard once vs 25-35K-token skills), vendor-neutral positioning, clone-and-go install (no Bun, no binaries), a simpler auditable Python compiler, and methodology parity on the rigor that matters.

**What to adopt (ranked):** (1) a real browser/test-execution QA loop, (2) semantic + event-sourced memory over `.resonance/`, (3) a multi-model second-opinion command, (4) per-version overlays, (5) auto-doc-drift in `/ship`. **What to NOT copy:** the heavy Bun/TS runtime and checked-in binaries, the 40K-token-per-skill weight, the founder-voice/promo lock-in, and the iOS-over-USB and prompt-injection ML apparatus (niche, heavy).

## 8. Loop engineering and the `/goal` question

**The state of the art.** The field has converged, and it is not AutoGPT. The reliable loop is a **bounded ReAct loop (reason, act, observe) grounded in external verification, backed by a plan and human checkpoints.** The load-bearing element is *grounded verification*: the agent must get ground truth from the environment at every step (executed tests, compiler errors, tool results), not self-judgment. Google DeepMind showed LLMs cannot reliably self-correct reasoning without an external signal, and can even degrade. SWE-bench-verified agents went from under 10% to over 70% in a year precisely by iterating against executed tests. Every serious system enforces two more disciplines: a **hard iteration/budget cap** (LangGraph's `recursion_limit`, OpenHands' `max_iterations` ~100 plus a cost cutoff and a StuckDetector, SWE-agent's $4/instance, Devin's ACU budget) and a **confidence or plan-approval gate** (Devin's color-coded confidence, Cursor's Plan Mode, OpenHands' ConfirmRisky). The discredited approach is exactly the opposite: hand an LLM a broad goal, let it self-grade "am I done" in natural language, with no ground truth and no stop. That reliably loops forever, hallucinates completion, and burns tokens.

**What Resonance already has.** More than it looks. The Verify Lock ("loop until proven, not until it looks right, no commit without evidence") is the loop doctrine, stated once and inherited everywhere. `/build` runs a TDD loop with a Recovery that routes to `/debug` after 2 failures. `/debug` runs a 7-step hypothesis loop with "wrong 3 times, reset." `/grill` is the plan-approval gate. Every skill carries a Definition of Done (the done-condition the SOTA loops need) and an "escalate after 3 tries" ceiling (the bound). The `.resonance/` memory is the cross-iteration state. What is missing is a single command that runs the *outer* loop across phases; today the human is the orchestrator connecting plan, build, test, audit, ship.

**Should Resonance add a `/goal` command? Qualified yes.** Resonance is unusually well-positioned for it because it already has the three things that make loops safe and most frameworks bolt on last: an explicit done-condition (DoD), a bound (escalate-after-3), and a verifier pattern (the `/audit` swarm). The pros: it turns the framework from a set of tools the human sequences into an agent that can carry a goal to a verified finish; it composes existing skills rather than inventing new behavior; and it directly expresses the Verify Lock at the top level. The cons and risks: without *grounded* verification it becomes an AutoGPT (this is why 3.1 and 3.2, the eval runner and the execution surface, are prerequisites, not optional); it needs hard budget/step caps and human checkpoints to stay safe; and it must not weaken User Sovereignty (the human still approves the plan and one-way doors).

**Recommended shape (do not build until the verifier exists).**
```
/goal "<outcome>"  (orchestration, manual-only)
  1. Grill the goal into a plan with an explicit, checkable Definition of Done  (/grill, /plan)  -> human approves
  2. Loop, bounded (max N iterations, budget cap, StuckDetector):
       build a slice (/build)  ->  verify with GROUNDED signals (run tests, run validate, /audit)  ->
       if DoD met: exit;  if progress: continue;  if stuck/regressed 3x: STOP and escalate
  3. Checkpoint to the human at each slice boundary (Devin-style), not every step
  4. /ship only on explicit approval
  5. Record decisions and learnings to .resonance/ each iteration
```
The done-condition must be a real check (tests pass, validator clean, audit APPROVE), never the model's own "I think I'm done." Build the eval runner and a test-execution surface first; then `/goal` is a safe, differentiated capability. Building it before them would be the one move that could make Resonance worse.

## 9. Prioritized recommendations

Ranked by leverage. The top three are prerequisites for elite; the rest are hygiene and depth.

**R1. Build the eval runner (`run_evals.py`).** Close the biggest hole. Feed each golden case to a model with and without the skill, grade against `expected_behavior` (LLM-as-judge for subjective, executed checks where possible). This finishes eval-first, makes skill quality measurable, and is the grounded verifier a `/goal` loop needs. Steal GStack's tiering (free static, then LLM-judge, then E2E) with diff-based selection to stay cheap.

**R2. Make the validator cross-skill aware.** Add checks for the exact drift this audit found: orphan reference files (exists but unlinked), duplicate reference files across skills (identical or diverged), and near-duplicate names. One pass would have caught the skill-author duplication, the `style_matrix` divergence, and 45 orphans. This is the deterministic Layer-3 fix that keeps the library clean automatically.

**R3. Give the agent eyes: a test/browser execution loop.** The single biggest capability gap versus GStack and the SOTA. Add an on-demand execution surface to `/test` (prefer `npx playwright` over a checked-in binary, to protect clone-and-go): navigate, reproduce, screenshot, fix, re-verify, write the regression test. This is also what makes `/goal` real.

**R4.
